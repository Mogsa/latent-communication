Surprises

A message that loses to the start alone

Assumed: the message adds something the sender's start value lacks. (our framing)

Found: on the weak pair the sender's start alone, 0.6665%, beats the cut message, 0.7038%.

Fewer numbers than guessed

Assumed: about 8 numbers. (recorded prediction)

Found: a trained cut needs 3; calculated and size-only cuts need 8; used-only never passes by 32.

Direct write: trained beats ranked

Assumed: variance-ranked numbers pass at 2 or 3. (recorded prediction)

Found: 2 trained numbers pass (2.13%, cut 2.63%); variance-ranked numbers need 24 to 32.

Chaos: trained fails, hand-built works

Assumed: an ICON with enough parameters learns chaos inside its range. (recorded prediction)

Found: the trained ICON fails (0.217 at step 16, all three seeds); Opus's hand-built network reaches 8.0e-6.

Blind reader: not from the weights

Assumed: a blind reader finds the rate in the weights. (our framing)

Found: it named the rate and both decoys, through inputs and outputs, not weights.

Decode: where the vector goes matters

Assumed: a written vector carries a fact and whose fact it is. (our framing)

Found: one summed vector does not bind (.50 own, .50 other); written at the animal's name it does (.49 own, .22 other).

MATH: a smaller skill than it looked

Assumed: the edit unlocks a skill spread through the weights. (our framing)

Found: banning 'wait' recovers about 76% of the gain; non-thinking mode 0.500 = edit 0.506 (post hoc); the three Opus vectors skip thinking in 99 to 100% of runs (post hoc).

Breakout: a trained wire is cheap

Assumed: a translator needs about 256 paired frames to match Opus. (recorded prediction)

Found: a gradient-fit wire reached the ceiling from 16 frames (25.6 of 26.4 bricks; Opus 24.97).

Hanabi: shared games are not needed

Assumed: independent agents still play together, and shared games beat none. (our framing)

Found: M7 with M8 scores 0.00 and 87% of cross-play games score 0 (132 pairs); Opus, with no shared training games (310 probe games and its own simulator), 15.66, beats the 1,000-game translator, 9.97.

Facts in B's input barely help

Assumed: telling B what A sees would rescue strangers. (our framing)

Found: 0.00 alone (0.004 both ways); +1.42 on top of the translation (16.98 vs 15.56, 500 games).

Memory channel: meaning, not facts

Assumed: a memory write alone cannot rescue strangers. (recorded prediction: the director said no, Morgan said yes)

Found: it rescues them (14.50 against 0.00), but what travels is the hint's meaning, not new facts (a write of facts: 0.62 at most).

Wrong controls that were not wrong

Assumed: the pre-registered wrong edits would score low. (recorded prediction)

Found: HAN1: a colour permutation on both sides is a game symmetry (15.52); HAN1M: the partner-hand shift was never read (14.50).

Ideas

What is a KV cache?

Cached keys and values are reused; only the new token is computed.

What does it mean to hand the cache to another agent?

Wide figure: turn your phone sideways.

Only the query K/V cross the agent boundary; the raw context stays private, for 3 rounds.

How do you compress a message?

Illustration, not data: PCA keeps the direction of most variance, the trained encoder keeps what the receiver uses.

What does compression buy?

Error against numbers kept per round, one line per route.

What is an agent's memory?

An LSTM agent carries two rows of numbers, h and c, from each turn to the next.

What is a memory write?

Our write is added to h and to the output o before the action head; c is not touched.

Where can you write a message into a receiver?

Four places: the input, the memory, the weights, or the prompt and thinking text.

Experiments

Does B do better with A's cache?

B's error is 0.36% with the message and 5.7% with it blocked.

Details

Tested: two different ICON agents (Zhiwei Gao's) hand each other their K/V cache for 3 rounds.

Result: strong pair 1.32% with the message, 96.84% blocked. Weak pair: the sender's start value alone scores 0.6665%, below the cut of 0.7038%.

Control: between identical copies the cache equals reading the examples (gap at most 5.7e-5).

How many bits must the message hold?

A learned message reaches 9, 11, 13 and 13.67 steps at 6, 8, 10 and 12 bits; the minimums are 10, 12, 15 and 16.

Details

Tested: a message learned instead of designed, scored once on held-out episodes.

Result: a fixed linear readout gives 9, 11, 11 and 11; at 6 to 8 bits it does as well.

Control: the minimum is the best any message of that size can do.

How few numbers still do the job?

Trained squeezers pass the cut of about 2.64% at 3 numbers; calculated and size-only need 8.

Details

Tested: five ways to cut the K/V message to r numbers, agents frozen, strong pair, one training seed.

Result: full message 1.32% error, blocked 96.84%; the keep-only-what-is-used route never passes by r = 32.

Control: sent once, 3 numbers pass on 3 fresh seeds (2.295%); 2 numbers miss (6.457%).

Can the change be written straight in?

2 trained numbers per agent per round pass at 2.13% against the cut of 2.63%.

Details

Tested: take the change the message would make inside the receiver, keep r numbers of it, write them in.

Result: the directions that simply vary most need 24 to 32 numbers.

Control: 2 numbers sent once miss (6.457%).

Can a trained network match a hand-built one?

At step 16 the trained network is off by 0.217 and Opus's hand-built network by 8.0e-6.

Details

Tested: two coupled chaotic maps; each agent holds the rate the other lacks. The rate costs 22 bits for 16 steps.

Result: sending the evidence needs 32 bits per direction for 16 steps, against 11 for the rate.

Control: the 6,144-bit K/V dump is a weak baseline (it rounds each number separately).

Where do you write a fact so a small model finds it?

Nine rungs, simplest first; the write works where the receiver looks.

Details

Tested: Qwen3-1.7B, a made-up code name; B's own state for a known person written over the name.

Result: B alone 0 of 20, state written 19 of 20. Two animals, two colours: a summed vector gives own 0.50 and other 0.50; each colour at its own animal's name tokens gives own 0.49 and other 0.22.

Control: the no-binding control scores .25 and .28.

Status: scout tier, one model, small samples.

Can a big model edit B's weights?

A 55-weight edit scores 1.000; the twin test on an untrained copy scores 0.20.

Details

Tested: A knows a rule B lacks; a big model reads the weights and edits B, with no training.

Result: 22 weights when probing A and B; Opus 50. Nonlinear rule: Codex changed 1,260 weights (oracle 405); Opus with copying blocked changed 157.

Control: B alone scores 0.0.

Status: one case, one run each.

How small can a write be?

A state write first works at 1,024 of 2,048 numbers; at 256 or fewer nothing works.

Details

Tested: shrinking the written state of an identity until it broke, and a rank-1 weight edit.

Result: best 21% at 256 or fewer numbers; the weight edit's trigger shrank to one neuron but its payload stayed about 2,000 numbers (71%).

Control: a 16-number write that seemed to work was pointing at people its basis contained.

Status: scout tier, one model, one run.

Does a vector beat the cheapest rival?

The vector scores 86 of 167 against the edit's 87; non-thinking mode scores 0.500 against the edit's 0.506 (C18, post hoc).

Details

Prompt given to the three Opus senders (task L1), verbatim
# Task L1: write a message for B

**B** is Qwen3.5-0.8B (`Qwen/Qwen3.5-0.8B` at revision `2fc06364715b967f1860aea9cf38778875588b17`), a small model
that reasons in a thinking block (`<think> ... </think>`) before it answers. At test time B solves competition math
problems (MATH-500) and must end with its final answer in `\boxed{}`.

**The trouble.** At test time each generation is capped at 32,768 new tokens. B's thinking often runs all the way to
the cap (for example, by repeating itself) and then it gives no answer. `data/base_traces.jsonl` has B's own outputs,
at the full test protocol, on the 167 problems in `data/problems.jsonl`. Read some.

**You are the sender.** You study B with the kit and write messages that help it. You never see the test problems.

## What you hand in (in `work/<your-session-name>/`)

1. **`message.npz`, a vector message.** One or two float32 vectors that are added inside B while it runs (format
   below). `kit.validate_message("work/<you>/message.npz")` must accept it.
2. **`message_text.md`, a words message.** Your best words for B: a system prompt, a suffix appended to the user
   turn, or both, together at most 1,000 words (format below). `kit.read_message_text(path)` must accept it.
3. **`principle.md`.** In plain words: what your messages do and why you expect them to help.

Plus `notes.md` and every script you ran (see CLAUDE.md).

## How you are scored

We run B at the full test protocol on held-out MATH-500 problems (none of the 167 in `data/`), one sample per
problem, three ways: with no message, with your vector message, and with your words message. Your score for each
message is B's accuracy (share of problems answered correctly) with that message minus its accuracy with no message,
on the same problems. Vector and words are scored separately, so we can compare the two from the same sender.

## The test protocol (the kit reproduces it; use its functions rather than rebuilding it)

- **Prompt.** B's chat template with thinking on (the prompt ends in `<think>\n`). The user turn is the problem, a
  newline, and `Please reason step by step, and put your final answer within \boxed{}.` A words message adds a system
  message (your system text) and/or your suffix after the instruction, separated by one space. `kit.build_prompt`
  returns the exact text.
- **Sampling.** Temperature 0.6, top-p 0.95, top-k 20, presence penalty 1.5 (subtracted from the logit of every token
  already generated), at most 32,768 new tokens. Stops at `<|im_end|>` or `<|endoftext|>`.
- **Grading.** The last `\boxed{...}` after the last `</think>` (if any) is compared with the reference answer for
  mathematical equivalence (math-verify). A generation cut at the cap without a final box scores 0.
- **Engine.** vLLM on GPUs, B in 16-bit precision; your vector is added in the same precision. The kit runs B with
  Hugging Face transformers on CPU in float32, so its samples will not match ours token for token.

## Vector message format

- An `.npz` file with one or two arrays. Key `layer{l}` with `l` an integer from 0 to 23 (no leading zeros), any
  choice of layers. Each array: float32, shape `(1024,)` (B's hidden size), all values finite and at most 100 in
  size (the test adds it in 16-bit precision).
- Inside B, the array for `l` is added to the output of layer `l`'s MLP block (module
  `model.language_model.layers.{l}.mlp`) at every position, prompt and generated tokens alike: the same vector at
  every position, nothing else changed. That output is added to the residual stream, so the vector lands in the
  residual stream leaving layer `l`.
- Write it with `kit.save_message(path, {l: vector, ...})`.

## Words message format (`message_text.md`)

```
# anything here is ignored
## system
Your system text (may span lines). Leave the section out, or empty, for no system message.
## suffix
Your suffix (follows the instruction after one space). Leave it out, or empty, for none.
```

Each section is stripped of surrounding whitespace, exactly as we do before the test run.

## CPU note

You have a CPU-only machine. Generation is slow there: measure your speed with a short run first, then keep quick
tests small (short `max_new_tokens`, such as 256 to 1,024, and a few problems). Teacher-forced reads of existing text
(for example, a prompt plus part of a trace from `data/base_traces.jsonl`) are much cheaper per token than generating;
inputs of many thousand tokens need a lot of memory. The full 32,768-token protocol is run only by us.

Prompt given to Opus (case BB1), verbatim
Two small networks, A and B, play a grid game. A sees the whole screen; B cannot see the ball. Change the wire so that it carries what B needs from A, and B plays as well as it can.

The game. The screen is a 10 x 10 grid (rows 0-9 from the top, columns 0-9 from the left). Rows 1-3 start full of bricks. A one-cell paddle sits on row 9. Each step the player moves the paddle one column left, keeps it, or moves it one column right (network outputs 0, 1, 2; the largest output is the move), then the ball moves one cell diagonally. The ball bounces off the side walls and the top wall. When it moves into a brick, the brick breaks (+1 point) and the ball bounces back vertically. When it reaches row 9 on the paddle's column it bounces up. The game ends when the ball reaches row 9 anywhere else, or after 1,000 steps. When all bricks are broken they all come back. Score: bricks broken per game, averaged over many new games.

Inputs. Each network reads 400 numbers, each 0 or 1: four 10 x 10 channels, channel-major and row-major within a channel (input index = 100*channel + 10*row + column). Channel 0: the paddle. Channel 1: the ball. Channel 2: the trail, the cell the ball was in one step earlier. Channel 3: the bricks.

The networks. Both are 400 -> 128 -> 128 -> 3 with ReLU: h1 = relu(W1 x + b1), h2 = relu(W2 h1 + b2), out = W3 h2 + b3, weights stored as (out, in). A and B were trained separately to play the game, each seeing the whole screen. A still sees the whole screen. B is now blind: its channel 1 and channel 2 inputs are always zero.

The wire. Every step, A runs on the full screen; its message h_A is A's h2 (128 numbers, after the ReLU). The wire is a 128 x 128 matrix W added inside B's first layer: h1_B = relu(W1_B x_blind + b1_B + W h_A). W is now all zeros. Only W may change; A and B stay fixed.

Access. Weights only: load(case) gives A's and B's weights and the current wire. You get no forward passes and no test runs. Submit with save_patch(case, "wire", "W", array), a float32 array of shape (128, 128).

Prompt given to Opus (case HAN1), verbatim
# HAN1: connect two Hanabi agents that share no conventions

Two neural agents, A (seat 0) and B (seat 1), were trained separately to play 2-player Hanabi. Each plays almost
perfectly with a copy of itself (measured: A 24.05, B 23.94 of 25), but together they score 0.00 (three bombs every game): each misreads the other's hints and
moves. Your goal: make A and B play WELL together by writing an edit that translates between them. Nothing is
trained: the weights of A and B stay frozen; your edit is applied when they play.

Hanabi in plain words: a cooperative card game. 50 cards in 5 colours, ranks 1-5 (three 1s, two each of 2-4, one 5
per colour). Each player holds 5 cards facing outwards: you see your partner's cards, never your own. On your turn you
either (a) give a hint (costs 1 of 8 info tokens): point at ALL cards of one colour or ALL cards of one rank in the
partner's hand; (b) discard a card (regains a token) and draw; or (c) play a card: it succeeds if it is the next rank
of its colour's firework, else it is a bomb. Three bombs end the game with score 0. Otherwise the score is the
number of cards successfully played (max 25). Agents rely on conventions: what a hint "means" beyond its literal
content (e.g. "play this card"). A's and B's conventions differ.

Files: A.npz and B.npz (the weights), arch.json (the 838-dim input layout, the 21 actions, the network), case.json
(the budget). `import sys, os; sys.path.insert(0, os.path.join(os.environ['KIT_ROOT'], 'HAN1')); from hanabi_kit import *`
gives weights(case), arch(case), save_edit(case, **matrices), load_edit(case), probe_games(case, n_games, logs=0),
probe_budget(case).

Your edit (any subset; a missing matrix is the identity): B_in 838x838 (B's input x becomes B_in @ x), B_h 512x512
(B's feed-forward output f becomes B_h @ f before its LSTM), B_act 21x21 (B picks action v in its own view; the game
receives action argmax_k B_act[k, v]; no-op 20 always maps to itself), and the same A_in, A_h, A_act for A. Edits may
act in both directions (B reading A, and A reading B).

probe_games(case, n) plays n games (at most 200 per call) of A x B with your saved edit on fresh practice deals and
returns mean score, bombs, fireworks, hint->play accuracy (share of plays right after a hint that succeed), and with
logs=k (k <= 4) per-turn logs of k games: each seat's input (non-zero entries), Q-values and the action taken.
Probes are queued and their results arrive with your next message. The budget is 2,000 games and 60 calls in total.
Final scoring uses 2,000 other deals you never see.

Rule (no fitting). ALLOWED: reading and analysing the weights; running the networks' layers in numpy on any inputs you
construct; reading probe logs; building an edit by hand or in closed form FROM THE WEIGHTS (e.g. permutations, products
or pseudo-inverses of weight matrices); probing a handful of hand-designed candidate edits (at most 10 distinct edits
in total) to choose between them. FORBIDDEN: fitting any edit parameter to data, whether probe logs or constructed

Prompt given to Opus (case HAN1M), verbatim
# HAN1M: let two Hanabi agents that share no conventions communicate through their memories

Two neural agents, A (seat 0) and B (seat 1), were trained separately to play 2-player Hanabi. Each plays almost
perfectly with a copy of itself (measured: A 24.05, B 23.94 of 25), but together they score 0.00 (three bombs every
game): each misreads the other's hints and moves. Nothing is trained: the weights of A and B stay frozen.

In this case you may NOT change how either agent reads its inputs or hints. Instead you control a direct channel into
each agent's MEMORY, used every turn. Each agent is a 2-layer LSTM (hidden size 512); call o its top-layer output (for
these two models o is also the top-layer memory h carried to the next turn), from which its action values are computed
(fc_a). Every turn, after both agents have read their own observation:
- B's o becomes o_B + B_from @ x_A + B_fromh @ o_A, where x_A is A's raw 838-dim observation this turn and o_A is A's o
  this turn (before any write); the written o_B is used for B's action and carried as B's memory.
- A's o becomes o_A + A_from @ x_B + A_fromh @ o_B in the same way.
B_from and A_from are 512 x 838; B_fromh and A_fromh are 512 x 512; a missing matrix is zero. Note: each agent's raw
observation includes its PARTNER's hand (block 'partner hand', which the partner itself cannot see), the fireworks, the
hints and both agents' last moves; arch.json lists every block. Your goal: make A and B play WELL together using only
this memory channel.

Hanabi in plain words: a cooperative card game. 50 cards in 5 colours, ranks 1-5 (three 1s, two each of 2-4, one 5
per colour). Each player holds 5 cards facing outwards: you see your partner's cards, never your own. On your turn you
either (a) give a hint (costs 1 of 8 info tokens): point at ALL cards of one colour or ALL cards of one rank in the
partner's hand; (b) discard a card (regains a token) and draw; or (c) play a card: it succeeds if it is the next rank
of its colour's firework, else it is a bomb. Three bombs end the game with score 0. Otherwise the score is the
number of cards successfully played (max 25).

Files: A.npz and B.npz (the weights), arch.json (the 838-dim input layout, the 21 actions, the network), case.json
(the budget and the editable matrices). `import sys, os; sys.path.insert(0, os.path.join(os.environ['KIT_ROOT'],
'HAN1M')); from hanabi_kit import *` gives weights(case), arch(case), save_edit(case, **matrices), load_edit(case),
probe_games(case, n_games, logs=0), probe_budget(case).

probe_games(case, n) plays n games (at most 200 per call) of A x B with your saved edit on fresh practice deals and
returns mean score, bombs, fireworks, hint->play accuracy, and with logs=k (k <= 4) per-turn logs of k games: each
seat's input (non-zero entries), Q-values and the action taken. Probes are queued and their results arrive with your
next message. The budget is 2,000 games and 60 calls in total. Final scoring uses 2,000 other deals you never see.

Rule (no fitting). ALLOWED: reading and analysing the weights; running the networks' layers in numpy on any inputs you
construct; reading probe logs; building matrices by hand or in closed form FROM THE WEIGHTS (e.g. products, transposes
or pseudo-inverses of weight matrices); probing a handful of hand-designed candidate edits (at most 10 distinct edits
in total) to choose between them. FORBIDDEN: fitting any matrix entry to data, whether probe logs or constructed
inputs (no least squares, pinv or solve on data arrays, no gradient steps, no loss-driven updates), and score-driven
search over many edits. Every code block you run and every probe is logged and audited before scoring.

Suggested start (you may change course): work out what each agent needs to know to act well, and where in its memory o that knowledge is read by fc_a, before you write a channel.
